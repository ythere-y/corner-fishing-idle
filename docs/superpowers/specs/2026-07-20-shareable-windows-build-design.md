# Windows 可分享内测版设计

日期：2026-07-20  
状态：Owner 已于 2026-07-30 批准（Windows 免安装 ZIP；接受未签名内测包的 SmartScreen 提示）
目标分支：`feat/shareable-windows-build`

## 1. 目标与成功标准

首个发布里程碑是一个可信的 Windows 免安装内测包。没有安装 Godot 的朋友或比赛评委下载 ZIP、解压并双击后，应在 3 分钟内开始游玩。

成功标准：

- 仓库内有可复现的 Godot 4.6 Windows Desktop 导出预设。
- 本地一条命令能生成命名稳定的 ZIP，例如 `Backpack-and-Bait-v0.1.0-windows-x86_64.zip`。
- ZIP 只包含运行游戏所需文件和玩家说明，不包含源码、开发存档、测试截图或构建缓存。
- 包内默认进入正式游戏，开发测试模式关闭；首次启动走开场故事和角色选择。
- 发布前检查会阻止验证失败、版本格式错误、缺少产物或误打包开发文件的构建。
- GitHub Actions 能在版本标签触发时复现同一产物，并把 ZIP 附到 GitHub Release。
- Windows 实机清单通过后，才能把 Release 从 draft 改为公开。

## 2. 发布阶梯

### 阶段 1：Windows 免安装内测包

本设计覆盖此阶段。目标用户是朋友和比赛评委，分发渠道以 GitHub Release 附件或直接传 ZIP 为主。

### 阶段 2：比赛双平台包

后续补 macOS 构建、Developer ID 签名、公证、比赛说明页和演示材料。macOS 未签名包不作为面向陌生用户的正式交付物。

### 阶段 3：公开持续发布

后续评估 itch.io、稳定版通道、更新提示、崩溃反馈和正式隐私/许可材料。自动更新器、Steam SDK、云存档和账号系统不进入阶段 1。

## 3. 构建结构

### 3.1 Godot 导出预设

新增受版本控制的 `export_presets.cfg`，预设名固定为 `Windows Desktop`，目标架构为 x86_64，使用项目当前 GL Compatibility 渲染路径。导出文件名由构建脚本决定，预设不写个人机器上的模板路径、证书或密钥。

游戏可执行文件使用英文 ASCII 名 `BackpackAndBait.exe`，降低压缩、命令行和部分杀毒软件处理中文路径时的兼容风险；窗口内产品名仍为“背包钓鱼手记”。

### 3.2 版本真值

版本号以 `project.godot` 的 `application/config/version` 为唯一真值，使用 SemVer，例如 `0.1.0`。构建脚本从这里读取版本，不在脚本、工作流和文档中重复维护。

版本标签格式为 `v<版本号>`。发布工作流必须校验标签与项目版本一致，不一致则失败，避免发错包。

### 3.3 本地构建脚本

新增 `tools/build_release.sh`，职责保持单一：

1. 检查 Godot 版本为 4.6 系列且可执行文件可用。
2. 检查工作树内受版本控制文件没有未提交改动；允许本地 `.godot/` 等已忽略缓存存在。
3. 运行首次无界面导入，再运行 `tools/validate_game.gd`，要求结果包含 `0 失败` 且进程成功退出。
4. 读取并校验项目版本。
5. 清理并重建仓库内已忽略的 `dist/<version>/` 精确目录。
6. 使用 release 模式导出 Windows 文件。
7. 复制玩家说明和必要许可文件。
8. 校验白名单内容后生成 ZIP 和 SHA-256 校验文件。

脚本默认只构建，不上传、不创建标签、不创建 Release，避免本地测试意外产生外部状态。

## 4. 玩家交付物

ZIP 顶层目录固定为 `Backpack-and-Bait-v<版本号>-windows-x86_64/`，其中仅包含：

- `BackpackAndBait.exe`
- Godot 导出的配套 `.pck`（若采用嵌入 PCK，则不单列）
- `开始游玩.txt`
- `LICENSE` 或阶段 1 所需的许可声明

`开始游玩.txt` 使用简体中文并包含：

- 解压完整 ZIP 后双击 `BackpackAndBait.exe`，不要直接在压缩包内运行。
- 游戏是透明桌面挂件，默认位于右下角；如何拖动、缩放、打开设置和退出。
- Windows SmartScreen 可能因内测包未代码签名而提示“未知发布者”；说明校验 SHA-256 的方法，不引导用户关闭系统安全功能。
- 存档位于 Godot `user://` 对应的 Windows 用户数据目录；重装/替换游戏包不会自动删除存档。
- 如何在游戏内开启新存档，以及出现问题时需反馈的系统版本、显示缩放比例和复现步骤。

## 5. GitHub 自动发布

新增 GitHub Actions 工作流，采用固定版本的 Godot 4.6 和匹配的导出模板。工作流分两种触发：

- Pull Request / 手动触发：运行导入、验证和 Windows 导出冒烟检查，保存短期 artifact，不创建 Release。
- 推送 `v*` 标签：再次完整验证，校验标签与项目版本一致，生成 ZIP 与 SHA-256，并创建 **draft Release**。

工作流权限遵循最小权限：普通构建只读仓库；发布 job 才授予 `contents: write`。第三方 Action 固定到明确版本；不引入证书、Steam 密钥或个人凭据。

Release 保持 draft 是明确的人工关卡。Owner 在 Windows 实机清单通过后手动公开，避免 CI 成功被误解为桌面行为已经验证。

## 6. 发布前验证

### 6.1 自动检查

- Godot 首次导入成功。
- `tools/validate_game.gd` 为 `0 失败`。
- Release 导出成功，可执行文件和 PCK 存在且非空。
- ZIP 内容符合白名单，不含 `.godot`、`user://` 数据、`.import` 噪声、测试截图、源码或日志。
- 项目版本、标签、ZIP 名和顶层目录一致。
- 计算并发布 SHA-256。

### 6.2 Windows 实机放行清单

至少在一台 Windows 10/11 x86_64 机器上，以全新解压目录和新用户存档验证：

- 双击启动、首次引导、角色选择和首轮钓鱼正常。
- 透明背景、逐像素点击穿透、置顶、拖动和缩放正常。
- 100%、125%、150% DPI 下挂件没有被 Region 裁空。
- 最小化、恢复、切换显示器或分辨率后仍可交互。
- 中央 modal 可打开、拖动和关闭。
- 自动存档、退出存档、重启读取和“开启新存档”正常。
- 无 Godot 编辑器或运行库的干净机器也能启动。
- 退出后进程结束，无残留窗口。

实机验证结果记录在对应 Release/PR 描述中。没有通过此清单的构建只能标为内部构建，不能公开称为可发布版本。

## 7. 错误处理与可恢复性

- 缺少导出模板时，构建脚本给出明确安装提示并退出，不下载未知文件。
- 验证或导出失败时保留日志路径，但不生成看似成功的 ZIP。
- `dist/` 全部忽略，构建只删除脚本自己解析出的精确版本目录，不删除工作区或用户目录。
- CI 上传失败不会修改代码或标签；Release 保持 draft，可重新运行后人工核对附件。
- 玩家存档继续使用现有原子写、`.bak` 回退和迁移机制；发布工程不改变存档格式。

## 8. 文档同步

实施时同步：

- `README.md`：增加“下载试玩/本地构建/存档位置”入口，并区分源码运行与发行包运行。
- `ROADMAP.md`：把 Windows 可分享内测包列为当前发布里程碑并记录完成状态。
- `BACKLOG.md`：记录选择“Windows ZIP → 双平台比赛包 → 公开发布”的原因和阶段边界。
- 若仓库当前没有清晰的软件许可证，发布前必须由 Owner 选择许可证；不能擅自假定美术、音频和代码均可按某个开源许可证再分发。

## 9. 明确不做

- 不制作安装器，不写注册表，不申请管理员权限。
- 不自动上传玩家数据，不新增遥测、账号、云存档或联网奖励。
- 不绕过 SmartScreen，不指导玩家关闭 Defender。
- 不在本阶段处理 macOS 签名、公证、Steam 或付费发行。
- 不把 CI 构建成功等同于 Windows 透明窗口实机验收成功。

## 10. 实施拆分

实现按可独立审查的顺序推进：

1. 版本真值、导出预设和本地构建脚本。
2. 玩家说明、包内容白名单和构建自检。
3. GitHub Actions 验证与 draft Release。
4. README、ROADMAP、BACKLOG 同步。
5. 本机构建验证；Windows 实机验证作为公开 Release 前的人工关卡。

以上五项可在一个发布工程 PR 中完成，因为它们共同定义同一个可交付构建链路，且不修改玩法与存档结构。
